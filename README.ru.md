# sysblink

[![ci](https://github.com/esnond/sysblink/actions/workflows/ci.yml/badge.svg)](https://github.com/esnond/sysblink/actions/workflows/ci.yml)

sysblink превращает свободный светодиод в живой индикатор системы. вы выбираете
диод и патч, установщик собирает маленького демона из шаблона, компилирует
его и отдает вашей системе инициализации. после этого диод показывает
загрузку процессора, памяти, диска, сети, температуру или то, за чем
следит выбранный патч, и продолжает делать это после перезагрузки.

проект написан при помощи ии.

страница проекта: https://esnond.github.io/sysblink/

статус: работает на живом ноутбуке с 30 октября, два демона под systemd на
50 гц, ноль перезапусков за первые 7 часов. другие дистрибутивы и другие
диоды пока не проверялись.

## требования

* linux со светодиодами sysfs в /sys/class/leds
* компилятор c: cc, gcc или clang
* python3 для установщика
* root нужен только для установки и удаления служб

## быстрый старт

    cd sysblink
    python3 sysblink.py

установщик спросит язык, покажет доступные диоды и патчи, спросит частоту
обновления и соберет демона в build/. положительный ответ на вопрос о
службе регистрирует его в найденной системе инициализации, этот шаг
требует sudo. если меню надоели, у всего есть флаги, они ниже.

## файл настроек

отвечать на одни и те же вопросы каждый раз надоедает, поэтому установщик
читает значения по умолчанию из sysblink.conf рядом с sysblink.py. образец лежит в
sysblink.conf.example, скопируйте его и сократите:

    # sysblink.conf
    lang = ru
    hz = 20
    init = systemd
    led = input13::scrolllock
    patch = cpu

интерактивное меню берет диод, патч, частоту и бэкенд отсюда, когда вы
просто нажимаете enter, а вопрос о языке пропускается, если lang задан.
флаг в командной строке всегда сильнее файла. неизвестные ключи
игнорируются, так что туда можно писать и заметки.

два ключа меняют то, за чем следит демон: disk закрепляет блочное
устройство для патча диска, iface закрепляет сетевой интерфейс для патча
сети, пустое значение оставляет поведение по умолчанию. оба вшиваются в
бинарник при сборке, таков путь sysblink, поэтому смена означает
пересборку.

    disk = nvme0n1
    iface = wlan0

## использование из командной строки

у каждого шага есть флаг, поэтому инструмент пригоден для скриптов:

    python3 sysblink.py --list_leds
    python3 sysblink.py --list_patches
    python3 sysblink.py --list_inits
    python3 sysblink.py --build 'input13::scrolllock' cpu --hz 20
    sudo python3 sysblink.py --build 'input13::scrolllock' cpu --install
    sudo python3 sysblink.py --build 'input13::scrolllock' cpu --init openrc --install
    sudo python3 sysblink.py --remove
    sudo python3 sysblink.py --remove_all
    python3 sysblink.py --version

заметки, которые экономят время: имя диода это имя каталога в
/sys/class/leds, берите его в кавычки, некоторые имена содержат двоеточия.
имя патча можно давать с суффиксом .c или без. сборка не требует root,
диод пишет сам демон во время работы, sudo нужен только для части со
службой. есть и man страница: `man sysblink` после установки deb или
`man -l docs/sysblink.1` прямо из дерева.

## системы инициализации

установщик берет первый бэкенд, у которого сработал detect, выбор можно
задать флагом --init. порядок распознавания: systemd, openrc, runit, s6,
sysvinit.

* systemd: юнит в /etc/systemd/system, включается и запускается systemctl,
  юнит идет с базовым hardening вроде ProtectSystem и NoNewPrivileges
* openrc: скрипт openrc-run в /etc/init.d, добавляется в уровень default
* runit: каталог с run скриптом в каталоге служб, подхватывается runsvdir
* s6: каталог с run скриптом в каталоге s6, простая супервизия, эксперимент
* sysvinit: классический init скрипт в /etc/init.d с командами start, stop,
  restart и status, включается через update-rc.d или chkconfig
* none: ничего не найдено, бинарник собран, запускайте его руками

удаление показывает все службы sysblink, известные любому бэкенду, и убирает
созданные файлы, включая копию бинарника в /usr/local/bin.

## как это работает

engine.c содержит всего демона. раз за тик он спрашивает у патча уровень
от 0 до 100, масштабирует уровень под максимум каждого диода и записывает
его в файл яркости. установщик подставляет плейсхолдеры {{LED_COUNT}},
{{LED_PATHS}}, {{LED_MAXS}}, {{SLEEP_US}}, {{BLINK_HZ}}, {{BLINK_TICKS}},
{{PROC_ROOT}} и {{SYS_ROOT}}, вставляет патч вместо маркера
/* PATCH_INSERT */ и компилирует результат в стандарте c99 с O2. исходник
остается в build/, поэтому видно, что именно работает на вашей машине.

две детали, которые стоит знать. во первых, на старте демон пишет none в
файл trigger каждого диода, если такой есть, потому что триггер ядра
спорил бы с записями яркости, и после выхода демона триггер так и
остается выключенным, при желании его можно вернуть руками. во вторых,
демон завершается по SIGINT или SIGTERM и записывает 0 во все диоды на
выходе, поэтому остановленная служба оставляет диоды темными. а если
записи падают десять тиков подряд, например диод исчез из системы, демон
выходит с кодом 1 и позволяет системе инициализации перезапустить его.

## несколько диодов сразу

один демон может вести много диодов одним патчем, это удобно, когда у
клавиатуры есть ряд диодов блокировки, просящий дела. перечислите имена
через запятую:

    sudo python3 sysblink.py --build 'input13::scrolllock,input13::capslock' cpu --install

имя службы склеивается из имен диодов, масштабирование идет по каждому
диоду отдельно, поэтому бинарный диод при максимуме 1 просто моргает, а
диод подсветки при максимуме 255 плавно играет яркостью. интерактивное
меню принимает номера через пробел или слово all.

## предпросмотр перед установкой

прежде чем ставить службу, можно посмотреть, как патч ведет себя с
фейковым диодом прямо в терминале:

    python3 preview.py breathe --hz 60
    python3 preview.py cpu --hz 10 --once

первая команда открывает curses полосу, которую питает настоящий демон,
пишущий в фейковый файл яркости в build/, выход по q. вторая делает три
тика и печатает одну полосу, удобно для скриптов. это инструмент для
быстрой прикидки, доказательства дают автоматические проверки.

## готовые патчи

* cpu.c: загрузка процессора из /proc/stat
* mem.c: занятая память из /proc/meminfo
* swap.c: занятый своп, он же разобранный пример в руководстве
* disk.c: скорость диска из /proc/diskstats
* net.c: сетевой трафик из /proc/net/dev, loopback не считается
* thermal.c: температура из первой тепловой зоны
* battery.c: заряд батареи из sysfs, при зарядке диод моргает
* loadavg.c: минутная средняя загрузка на ядро
* heartbeat.c: классическое двойное моргание
* breathe.c: плавная волна дыхания на четыре секунды

патчи, измеряющие скорость, используют частоту тика BLINK_HZ, чтобы
переводить бюджеты из patches/config.h в пороги за тик, поэтому шкала
честная на любой частоте.

## свой патч

руководство лежит в docs/patches.ru.md, английская версия в
docs/patches.md. коротко: патч это один файл c в каталоге patches, он
определяет функцию int get_led_value(void) и возвращает число от 0 до 100
без сна внутри. проще всего начать со swap.c, это самый маленький патч,
который трогает /proc.

## разработка

    make test

гоняет четыре вида проверок. живые собирают каждый патч в движок со
строгими флагами c99, pedantic и всеми предупреждениями как ошибками,
затем запускают headless сессии против фейковых файлов яркости в build/ и
следят, чтобы патчи со временем доходили до яркой фазы, а остальные писали
вменяемые числа. проверочные указывают движку на копии /proc и /sys в
tests/fixtures и ждут точных значений, например память пишет 75, а патч
процессора дает пик ровно 20 на фикстурных числах. проверочные времени
скармливают демону /dev/full, доказывая, что неудачные записи завершают
его с кодом 1, и растят закрепленные источники в фикстурах, доказывая,
что выбор disk и iface действительно выбирает. питоновские покрывают
логику установщика, от разбора конфига до генерации файлов служб для
каждого бэкенда. BLINK_TICKS вшивает лимит тиков в демона, 0 значит
работать до сигнала, это и делает прогоны headless. тот же набор гоняется
на каждый push через github actions.

## структура

    sysblink/
      sysblink.py            установщик и сборщик
      preview.py             предпросмотр патча в терминале
      engine.c               шаблон демона
      patches/               десять патчей и config.h с общими порогами
      docs/                  руководство по патчам на двух языках, man
      tests/                 headless проверки, фикстуры и тесты python
      makefile               запускает проверки
      packaging/             deb скрипт и pkgbuild для aur
      site/                  страница проекта для github pages
      .github/workflows/     ci на push, деплой страницы, релиз deb по тегам
      CHANGELOG.md           история версий
      CONTRIBUTING.md        как собирать, тестировать и присылать патч
      SECURITY.md            приватный канал для уязвимостей

## упаковка

packaging/deb/build.sh собирает deb через dpkg-deb, при разработке пакет
собирался и проверялся на debian. он ставит установщик в /usr/bin/sysblink, а
дерево в /usr/share/sysblink, sysblink.py находит дерево там сам. packaging/aur/PKGBUILD
приложен для arch, но здесь не проверялся, на этой машине нет makepkg.

## ограничения

* battery.c опрашивает только BAT0, BAT1 и BATT, обход каталога sysfs
  потребовал бы dirent.h вне posix подмножества компиляции
* поддержка s6 рассчитана на простую супервизию, пакеты s6 rc не подключены
* калибровка disk и net подобрана вручную, бюджеты в patches/config.h
  можно подстроить под свое железо
* патчи скорости меряют между тиками, уснувшая машина может дать скачок
  счетчиков назад, патчи отвечают нулем на таком тике
* упакованный установщик собирает в /var/lib/sysblink, потому что каталог
  share принадлежит root, что соответствует его работе
