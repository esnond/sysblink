sysblinkсветодиод, который показывает систему

sysblink собирает маленького демона на c99 из шаблона и одного патча. демон раз в тик читает метрику из /proc или /sys и пишет уровень яркости в обычный светодиод через sysfs. никаких библиотек, никакой сборки мусора, один бинарник и один цикл.

статус: v1.0.0 живое железо: не проверялось linux, sysfs c99, без библиотек 5 систем инициализации 10 патчей лицензия mit

что это

у ноутбука есть ряд светодиодов, которые обычно мигают только при нажатии caps lock. sysblink находит их в /sys/class/leds, дает выбрать один или несколько, компилирует под них демона и, если попросить, ставит его службой в систему инициализации.

устройство простое: шаблон engine.c держит цикл, открытие файла яркости, обработку сигналов и масштабирование под максимум диода. патч это один файл c с единственной функцией int get_led_value(void), которая возвращает уровень от 0 до 100. установщик подставляет патч в шаблон, подставляет пути диодов, частоту и компилирует результат строгим gcc.

engine.c + patches/cpu.c + sysblink.conf
        |
        v
cc -std=c99 -pedantic -Wall -Wextra -Werror -O2
        |
        v
sysblink_input13_scrolllock   (16.7 кб)

исходник собранного демона остается в build/, поэтому видно ровно то, что работает на машине. это осознанно: никакой магии, никакой загрузки кода из сети, только текст, который можно прочитать.

зачем это

ядро умеет несколько готовых триггеров для светодиодов, но набор фиксирован и зависит от конфигурации ядра. sysblink дает любую метрику, которую можно прочитать из /proc или /sys, и работает там, где systemd нет.

три сценария, ради которых это писалось. первый: ноутбук, у которого индикаторы блокировки простаивают, теперь показывает загрузку процессора или сеть, и вы смотрите на знакомые лампочки вместо отдельного окна с htop. второй: домашний сервер с openrc или runit, где готовые решения требуют systemd. третий: собственная метрика, которую никто не реализовал, от температуры батареи до числа ssh сессий, это один файл на сорок строк.

честная оговорка: если вам нужен ровно классический heartbeat или активность диска, есть шанс, что триггер ядра уже это умеет и sysblink не нужен. проект про произвольные метрики и про системы без systemd.

как пользоваться

три команды до первого мигания. сборка root не требует, sudo нужен только на шаге установки службы.

git clone https://github.com/esnond/sysblink
cd sysblink
python3 sysblink.py

установщик спросит язык, покажет диоды, покажет патчи, спросит частоту и соберет демона в build/. на вопрос о службе можно ответить нет и просто запустить бинарник руками.

у каждого шага есть флаг, поэтому меню можно объехать полностью:

python3 sysblink.py --list_leds
python3 sysblink.py --build 'input13::scrolllock' cpu --hz 20
sudo python3 sysblink.py --build 'input13::scrolllock,input13::capslock' cpu --install
sudo python3 sysblink.py --remove_all
python3 sysblink.py --version

значения по умолчанию берутся из sysblink.conf рядом с установщиком, образец лежит в sysblink.conf.example. два ключа меняют источник: disk закрепляет блочное устройство, iface закрепляет сетевой интерфейс.

lang = ru
hz = 20
init = systemd
led = input13::scrolllock
patch = cpu
disk = nvme0n1
iface = wlan0

посмотреть патч до установки можно на фейковом диоде прямо в терминале:

python3 preview.py breathe --hz 60
python3 preview.py cpu --hz 10 --once

после установки deb появляется man страница: man sysblink.

как пятилетнему: вопросы и ответы

отвечает волк. он же маскот, он же автор.

что такое светодиод и при чем тут система?

это маленькая лампочка на корпусе. ядро linux отдает ее яркость как обычный файл: пишешь в него число, лампочка светится. значит любой показатель системы можно превратить в свечение, надо только вовремя писать число.

что такое патч?

один файл c с функцией get_led_value, которая возвращает число от 0 до 100. все. патч не открывает диод, не спит и не ставит службы, этим занимается движок. поэтому свой патч пишется за вечер, а руководство с примером лежит в docs/patches.md и docs/patches.ru.md.

почему не готовые триггеры ядра?

потому что их набор фиксирован и зависит от того, как собрано ядро, а мне нужна была своя метрика и работа без systemd. если вам хватает готового триггера, честно, используйте его, это дешевле.

нужен ли root?

для сборки нет. демон сам пишет в /sys/class/leds при запуске, а это обычно только root. установка службы в /etc и /usr/local/bin тоже требует sudo. поэтому сборка отделена от установки явно.

что будет, если диодом уже управляет ядро?

демон на старте пишет none в файл trigger своего диода, иначе триггер ядра перебивал бы записи яркости. после остановки демона триггер остается выключенным, вернуть его можно руками. это поведение описано в readme, потому что оно меняет настройку системы.

а без systemd заработает?

да. есть openrc, runit, s6 с простой супервизией, классический sysvinit и режим без установки, когда бинарник просто лежит в build и запускается руками. поддержка пяти бэкендов и режима без установки и есть причина, почему проект вообще появился.

сколько это ест?

бинарник 16.7 кб, rss 1.7 мб, один тик это одно чтение файла в proc и одна короткая запись в sysfs. при частоте 10 гц это ничто на фоне любого браузера.

почему максимум диода не 255?

потому что он у всех разный. у клавиатурных индикаторов max_brightness часто равен 1, у подсветки бывает 255. демон масштабирует уровень под каждый диод отдельно, бинарный диод моргает по порогу 50 процентов, аналоговый плавно играет яркостью.

это безопасно?

демон пишет только в brightness и trigger своих диодов, юнит systemd идет с ProtectSystem, ProtectHome и NoNewPrivileges, код собирается с pedantic и всеми предупреждениями как ошибками. но на живом железе проект пока не проверялся, это главный открытый пункт, и я не буду делать вид, что его нет.

кто это написал?

автор проекта при помощи ии. это написано в readme и повторяется здесь, потому что скрывать такой факт глупо, а проверить его легко.

установка

debian и ubuntu

пакет собран и проверен dpkg-deb на debian. ставит установщик, дерево, man страницу.

sh packaging/deb/build.sh
sudo apt install ./build/sysblink_1.0.0_all.deb
man sysblink

arch

pkgbuild лежит в packaging/aur/PKGBUILD, но не проверялся: на машине автора нет makepkg. считайте его черновиком.

из исходников

нужны cc и python3. живое дерево, без установки, только сборка в build.

make test
python3 sysblink.py

что не проверено

этот раздел важнее остальных. он будет сокращаться только по мере реальных проверок.

  1. живое железо: автор гонял headless проверки на фейковых файлах яркости, на настоящем ноутбуке установка не проверялась.
  2. arch: pkgbuild не запускался, makepkg на машине разработки нет.
  3. s6 rc раскладки не подключены, поддержан только простой supervised каталог.
  4. калибровка disk и net подобрана вручную, пороги живут в patches/config.h и зависят от железа.
  5. battery ищет bat0, bat1 и batt, другие имена в sysfs он не увидит.

тесты

доказательства, а не обещания. make test гоняет 25 проверок четырех видов.

живые собирают каждый патч строгим gcc и запускают headless сессию против фейкового диода. фикстурные направляют движок на копии /proc и /sys и ждут точных значений, например память пишет ровно 75. runtime кормит демону /dev/full и требует выхода с кодом 1 после десяти неудачных записей. python проверки покрывают установщик, от разбора конфига до генерации файлов служб для всех пяти бэкендов.

тот же набор запускается на каждый push через github actions, а по тегу собирается deb и уходит в releases.
